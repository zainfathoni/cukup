# Stage 5A: internal shadow evidence persistence

This experimental foundation implements only service-side persistence for ADR 0007. It does not make new measurements authoritative or claim cloud ingestion exists. `ServiceStore.shadow` is an internal caller-owned boundary, unused by production HTTP routes, the local receiver, and collectors. It reuses the unchanged pure closed parser/types, relocated to `service/harness-evidence-protocol.ts` with a compatibility re-export at `experimental/local-harness-evidence.ts`. This keeps the parser inside existing Docker build inputs and service publication path coverage without importing receiver, HTTP, runtime, or native collectors or changing workflows. That parser remains the single evidence validation authority.

## Contract

`append(input, receivedAtMs)` accepts exactly `{ executionSiteId, sourceSequence, envelope }`. The existing version-1 generic protocol envelope must contain exactly one valid engagement, execution start, or execution end. This wrapper is an internal persistence contract, **not a cloud wire schema**. An eventual uploader must durably assign source sequences before delivery; none is assigned or inferred here.

- Collector ID and execution-site ID are random UUIDv4 strings; identity comparison is exact and case-sensitive, as in the experimental receiver. The first accepted record binds its collector to one immutable site. This caller-supplied binding is **not authentication**, a Machine Label, or authorization to attribute remote work. Future cloud authentication must establish the actual execution-site binding before calling this boundary.
- Evidence IDs are globally unique within the shadow namespace, separate from legacy event IDs. Reusing one across collectors is an immutable conflict, not a duplicate. Segment IDs are scoped to the collector; one collector cannot close another's start.
- An exact duplicate matches evidence ID, collector/site, sequence, protocol version, sorted capability declaration, and canonical closed evidence. JSON object-key and capability order do not matter. Receipt time is excluded from identity and the original receipt time remains unchanged. Valid changes to any immutable value return `identity_conflict`; malformed records return `invalid_record`; unsupported protocol versions return `unsupported_version`, including on replay.
- Positive safe-integer source sequences strictly increase per collector; gaps are accepted, never backfilled. A new fact at or below the accepted high-water mark returns `invalid_order`. Exact old duplicates are checked first. Sequence is delivery order, not occurrence order. This does not retrofit sequences into the local receiver or its queue.
- Delayed occurrences have no age cutoff and retain their original wall time, timing provenance/precision, recovery status, and attribution snapshot. Future occurrence tolerance remains the parser's ten minutes. Receipt time does not move occurrence time; missing human origin, attribution, timing, starts, or ends are never inferred.
- Starts remain pending indefinitely until a later-sequence end for the same collector/segment has occurrence time greater than or equal to the start. Orphan and backwards ends return `invalid_order`; a second distinct start/end for an endpoint returns `identity_conflict`. Rejected ends are not retained or silently repaired. End evidence cannot include attribution; segment ownership stays on its start, including Unassigned. `segments()` returns the original endpoint records and pending/closed status, never duration or totals.
- Every append uses an immediate SQLite transaction. A new collector binding and its first evidence commit together, before `accepted`; exceptions roll back and propagate without payload logging. Validation rejections do not write. Records, bindings, sequence ordering, duplicate checks, and pending/closed state survive reopen. No raw rejected payloads or diagnostics are persisted.

## Storage and compatibility

Service schema **5** adds isolated STRICT `shadow_collectors` and `shadow_evidence` tables, uniqueness constraints, and UPDATE/DELETE refusal triggers. The canonical JSON columns contain only parser-accepted closed evidence and capability declarations, including occurrence basis, recovery status, and attribution—not an arbitrary metadata bag. Prompts, output, paths, tokens, cost, native thread/message IDs, and unknown fields are rejected. This is a reviewed application boundary, not containment of malicious in-process code or database administrators; allowed IDs cannot prevent covert encoding, as ADR 0007 states.

Migration follows the existing immediate transactional `user_version` convention. Versions 0–3 retain their existing upgrade steps; version 4 adds only shadow storage without rebuilding legacy tables. Failed DDL leaves the version and legacy state intact. Future service schemas are refused. Legacy v1/v2 wire schemas, tables, constraints, rows, source ownership, queued plugin payloads, aggregation, summaries, and dashboard behavior remain unchanged. Shadow data never enters legacy queries.

Tests cover schema/row equality around v4 migration and shadow writes, v1–v3 upgrades, future-version refusal, restart, exact replay, immutable and cross-source conflicts, sequence regressions, late evidence, orphan/backwards ends, start attribution retention, prohibited fields, injected transaction/migration failure, and append-only SQL mutation refusal. All databases are disposable local fixtures.

## Deployment implications and remaining scope

**This is not deployment-neutral:** service startup migrates its database to schema 5, even while no shadow caller is connected. An eventual main push may trigger service image publication and requires explicit owner approval. No push, deployment, production access, or production migration is part of this slice. Old schema-4 binaries refuse schema 5; any eventual rollout/rollback plan must retain accepted shadow evidence rather than downgrade or drop it.

Cloud authentication/API, collector upload, aggregation/union, cutover clipping, dashboard and coverage/synchronization presentation, historical migration/backfill, support claims, deployment, and owner-approved cutover remain separately reviewed later slices. This foundation neither infers legacy equivalence nor computes Working Time or Agent Runtime.
